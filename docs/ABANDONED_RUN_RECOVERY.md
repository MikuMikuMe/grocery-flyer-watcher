# Executable startup and abandoned-run recovery

Use the pinned offline `runtime_controller.py` command `recover` to generate a single local bundle for startup or recovery. This is not a scheduler or a delivery authorizer. Follow the existing native continuation, evidence, quality, publication and recipient safeguards.

The private request contains `action` (`start`, `recover_abandoned`, or `recover_start`), `expected_revision`, `checkpoint_sequence`, `verified_checkpoint`, `verified_no_other_writer`, and (for recovery) `verified_no_unresolved_delivery` and `latest_run` (actual native `id`, `recorded_status`, `scheduled_for`, `completed_at`, and `started_at` when available). For a new run include its unique `run_key`, actual `native_run_id` and `scheduled_for` if known, and actual UTC `observed_started_at` when either is unknown. Never substitute the previous invocation ID for the current one. Verify checkpoint schema, all native recipient uncertainty and single-writer evidence before making attestations. If they are unknown, stop unsafe recovery. Do not use recovery for PENDING, IN_PROGRESS, RESULT_SAVED or COMMITTED states; follow existing operation-specific reconciliation. A strictly later completed native record establishes supersession for an empty old run only with verified checkpoint and no other active writer; the old historical outcome remains unknown. When native identity/schedule was not exposed, require a later native start timestamp than the recorded local observation. Preserve exact prior outcome when known separately in history; do not infer success from scheduler completion.

```sh
python runtime-controller.py recover operation-journal.md --request event.json --history run-history.md --output next-operation.md --history-output next-history.md --handoff-output next-handoff.md
```

`recover_abandoned` closes the empty run without starting a fake invocation; `recover_start` also initializes the real current run; `start` initializes from IDLE or RUN_FINISHED. All outputs are separate new local files. Check exact current Library versions and native state before any writes. Upload history and handoff first (one batch), materialize both returned versions and compare exact bytes; then overwrite operation journal and materialize/compare its exact bytes. Treat the journal as the commit marker. Stable history keys and stable recovery body allow retry if interrupted before the final write. A START entry alone is not proof a run reached its WAL commit; reconcile orphan STARTs from actual native evidence. Never treat this as atomic multi-file storage or claim a journal upload succeeded from local output. No checkpoint increment or retailer completion during this path. After verified RUN_STARTED, continue actual planner/source work rather than return a startup report.
